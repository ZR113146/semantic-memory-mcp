# MCP 工具目录采用完整精简 L1，完整手册由 describe_tool 按需返回

## Summary

为什么 tools/list 应返回完整的精简工具目录，而不是固定 8 项分页或一次注入全部手册？

## Content

[Decision] MCP tools/list 必须一次返回完整的可调用工具目录，但只注入精简 L1 定义：每个工具保留名称、title、首句说明和结构化 schema，移除超过 80 字符的参数说明；完整用途与参数手册继续由 describe_tool 按需返回。不得用固定 8 项分页代替这种两层注入，因为不消费 nextCursor 的客户端会永久失去后续工具。

[Context] 2026-07-15 部署 ADR Markdown Mirror V1 后，adr_export 与 events 位于 tools/list 第 3 页，describe_tool 位于第 4 页，而当前 Codex 只暴露第 1 页。Git 历史证明 8c85330 已建立“完整精简目录 + describe_tool 按需全文”设计，随后 0d3e24c 引入的 8 项分页与它组合后产生能力回归。实测旧部署首屏为 11627 bytes、8 项且仍含长说明；恢复两层设计后为 14123 bytes、27 项、无长说明，describe_tool 单独返回完整手册。

[Rejected alternatives] (1) 一次返回 27 份完整手册：违背上下文预算约束。(2) 仅把 adr_export/events 调到前 8 项：只会让其他工具变得不可见，并掩盖客户端未翻页问题。(3) 保留分页并规定 V1 只走 CLI：会让已注册的 MCP 能力无法通过类型化工具调用。(4) 新增通用 call_tool 网关：扩大调度与校验表面积，现有精简目录已足够。

[Anchors] 历史提交 8c85330（slim tools/list + describe_tool）、0d3e24c（8 项分页）、df7c09a（ADR Markdown Mirror V1 基线）；实现位于 src/mcp/mcp.c，回归位于 tests/test_mcp.c。部署验证：MCP 140 passed/3 expected Windows skips，memory 52/52，两个 ADR mirror check=clean。
