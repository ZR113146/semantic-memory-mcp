# #768 兼容探针为什么对"空的旧 edges 表"改成 drop+重建自愈，而非 fail-open（否则不可重建的记忆库

## Summary

#768 兼容探针为什么对"空的旧 edges 表"改成 drop+重建自愈，而非 fail-open（否则不可重建的记忆库被永久锁只读）

## Content

[Decision] init_schema 的 #768 兼容探针：遇到缺 local_name_gen 生成列的旧 edges 表时，若该表为空则 DROP TABLE + 按当前 DDL 重建；仅当 edges 非空(真实图库)时才沿用原逻辑 fail-open。

[Context] #768 给 edges 加了生成列 local_name_gen(IMPORTS 去重判据)，SQLite 无法 ALTER 表级 UNIQUE，故探针原本对任何缺列的旧 edges 一律 fail 打开——本意是让"可重建的图库"删库重建。但 <project>-memory.db 携带拆库前(记忆与图谱共库时代)遗留的一张空 edges 表，且记忆库按红线不可重建；于是每次以读写打开(写路径要跑 init_schema)都在探针处 fail → resolve 返回 NULL → 写入报 "failed to append / project not found"，记忆库被永久锁死只读。这才是本会话记忆写入彻底失效的真正拦路 bug（cbm_now_ns 溢出与只读句柄复用是叠加症状，各修各的）。只读打开(query)跳过 init_schema，所以读一直正常、唯独写死——极具迷惑性。

[Rejected alternatives] (a) 数据修复(手动 DROP 每个记忆库的空 edges)——治标不治本，global/其他项目库同病要逐个 whack-a-mole。(b) 让记忆库根本不建图谱表——store_open_internal 通用、改动大。(c) 保持 fail-open——记忆库不可重建，等于永久锁死。空表 drop+重建零数据风险(edges 本就空、且记忆操作不用它)，是自愈的正解。

[Anchors] 提交 446c8cf，src/store/store.c 的 init_schema #768 探针分支(空 edges → exec DROP + 重跑 DDL)；调用链 cbm_store_open_path → store_open_internal → init_schema。排错全过程见 [[failed-to-append-three-root-causes]]。
