# 记忆 id 为什么用高精度单调时钟 cbm_now_ns 而非秒精度 memory_now_ms（根治同秒跨进程主键冲突）

## Summary

记忆 id 为什么用高精度单调时钟 cbm_now_ns 而非秒精度 memory_now_ms（根治同秒跨进程主键冲突）

## Content

[Decision] 记忆 id 的时间成分用 cbm_now_ns(高精度单调时钟，Windows 上是 QPC)，不用秒精度的 memory_now_ms。memory_now_ms 保留用于 created_at/last_hit_at/decay 等 wall-clock 语义字段。

[Context] memory_make_id 原来用 "<prefix>-<memory_now_ms>-<seq>"，但 memory_now_ms 是 time()*1000 秒精度，且 static seq 在每个 CLI 进程从 0 重置。同一秒内跨进程的两次写入生成相同 id → 主键冲突 → "failed to append memory event" 间歇失败。这是个影响真实使用的既有 bug：用户同秒连写两条，第二条静默失败。补充(2026-07-08)：id 唯一性依赖的时钟源 cbm_now_ns 本身后来在 Windows 上被发现有 uint64 溢出隐患(QPC count·1e9 溢出)，已在提交 446c8cf(src/foundation/platform.c)修复——本 id 修法所依赖的底座随后被再次加固。

[Rejected alternatives] 把 memory_now_ms 整体改成真毫秒——会破坏 created_at/decay 的 wall-clock 语义(cbm_now_ns 是单调时钟非墙钟)，且毫秒仍可能同毫秒撞。只改 id 生成最小且根治。

[Anchors] memory_make_id 时间成分换 cbm_now_ns；提交 96a5a21(2026-06-30，"make memory ids unique within the same wall-clock second"，当时改 src/store/store.c)。38f8d25 抽离后 memory_make_id 现居 src/memory/memory_store.c，仍调 cbm_now_ns(src/foundation/platform.c，其 Windows 溢出在 446c8cf 修复)。验证：8 次快速连写全成功(原约 50% 失败)。
