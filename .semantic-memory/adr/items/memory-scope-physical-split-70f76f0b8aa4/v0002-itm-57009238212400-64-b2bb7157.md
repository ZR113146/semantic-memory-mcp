## Content

[Decision] 记忆库从"project 单维物理切分"升级为"按作用域分层(project / global)"。新增 global 作用域库 <cache>/__global__-memory.db，scope_project=NULL 的记忆落此。所有项目检索时，除打开本项目 <project>-memory.db 外，额外 union 打开 global 库——高复用信息一次写入、各项目皆可见。范围不止用户画像：凡"项目间可高度复用"的信息(画像/偏好、跨项目通用经验/约定/参考)都应有一个 global 作用域的口子可写可读。

[Context] 现象(重建用户画像时暴露)：3 条 preference 画像落进了 D-semantic-memory-mcp-memory.db 而非用户级独立库——不是有人选择放这儿，而是写入时根本没有"项目无关"这个去处。根因是物理 vs 语义解耦不彻底：物理切分粒度只有 project 一维(cbm_memory_db_path 只把 project 拼进文件名)，而数据模型侧 user/global 是一等公民(检索 SQL 对 scope_user 宽松跨项目匹配；memory_infer_entity 把"有 scope_user、无 scope_project"归为 entity=user)。逻辑说"跨项目可见"，物理说"只能在写入它的那个项目里看见"——resolve_memory_store 一次只开一个项目 sidecar，画像即便 scope_project=NULL 也读不到。与当年记忆/图谱 -memory.db 拆分同构、低一层。改动面：cbm_memory_db_path 增加 global 路由(scope_project 空→global 库)；resolve_memory_store/resolve_global_memory_store 同时持有项目库+global 库句柄并 union(全局句柄独立 slot，切项目不驱逐)；写入侧高复用记忆正确置 scope_project=NULL；reindex/install 删库与 phantom-name guard 把 global 库纳入"持久、不可重建、排除删除"保护。

[Rejected alternatives] (a) 维持 project 单维物理切分——与 scope_user/global 跨项目语义自相矛盾，高复用信息物理钉死无处可读。(b) 用 SQL ATTACH 做跨库 union——store_authorizer 禁 ATTACH；改走分别开句柄、应用层合并(与 anchor-boost borrowed handle 同思路)。
