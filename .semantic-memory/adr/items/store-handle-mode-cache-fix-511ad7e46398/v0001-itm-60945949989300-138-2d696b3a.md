# 记忆 store 句柄为什么要按读写模式(而非仅项目名)缓存：只读句柄被写复用会 SQLITE_READONLY

## Summary

记忆 store 句柄为什么要按读写模式(而非仅项目名)缓存：只读句柄被写复用会 SQLITE_READONLY

## Content

[Decision] resolve_memory_store / resolve_global_memory_store 复用缓存的 store 句柄前，必须校验它能否服务本次请求：写请求(create)若命中一个只读缓存句柄，则 close 并以读写重开。用 store_handle_writable(sqlite3_db_readonly(db,"main")==0) 判定。

[Context] 原来句柄只按项目名缓存、忽略打开模式。读路径(retrieve)用 cbm_store_open_path_query 以 SQLITE_OPEN_READONLY 打开并缓存；召回钩子每轮先 retrieve，于是缓存里是只读句柄；紧接着的 events 写命中缓存、复用只读句柄 → INSERT 报 SQLITE_READONLY「attempt to write a readonly database」→ "failed to append memory event"。全新项目因为第一次访问就是写(拿到读写句柄)所以不复现——这也是本 bug 长期潜伏的原因。

[Rejected alternatives] 读路径也总是读写打开——读写打开会跑 init_schema，遇旧 edges 会触发 #768 探针(见 [[memory-db-empty-edges-selfheal]])，反而砸掉本可工作的读路径；且读不该要写锁。故按模式区分、写时才重开。

[Anchors] 提交 446c8cf，src/mcp/mcp.c 新增 store_handle_writable，并在 resolve_memory_store 与 resolve_global_memory_store 的缓存命中分支加"只读句柄遇写请求则重开"。排错手册见 [[failed-to-append-three-root-causes]]。
